## 一、交叉质询记录

### 1.1 对方案 A「Swiss 纯粹主义」的质询（未采纳历史方案）

**质询 A1: 6px → 2px 变化对现有用户的影响如何量化？**

| 维度 | 分析 |
|------|------|
| 影响范围 | 123 处 `rounded-[2px]` 实例分布在 31 个文件中，覆盖全部 6 个页面和 Studio 编辑器 |
| 视觉变化幅度 | 2px 圆角是"几乎直角"，6px 是"可见圆润"。6→2 是**从圆润变锐利**的质变 |
| 用户感知 | 影响所有可见卡片、按钮、输入框、面板的边角。用户不会注意到"圆角从 6 变 2"，但会感知"整体风格突然变锐利" |
| 回归风险 | 需回归测试全部 6 页面 + Studio 全功能。仅 `ThemesPage.tsx` 就有 11 处改动点 |

**回应**: 方案 A 的 9 分"业务根治"评分合理，但"场景兼容"得分 6 分**过于乐观**。123 处改动（非 50+）意味着更高的回归风险。建议将场景兼容调整为 **5 分**。

---

**质询 A2: 是否有数据支持"2px 更符合 Swiss 风格"的假设？（历史方案）**

| 证据类型 | 内容 | 可信度 |
|----------|------|--------|
| 设计规范 | Swiss/International 设计原则确实强调锐利几何、克制装饰（历史方案依据） | 高 |
| 参照项目 | swisspost/design-system、IBM Carbon 用 0-2px | 中（参考集合偏差） |
| 代码注释 | `globals.css` L67 "softly-rounded surfaces (gentle, not sharp-cornered)" — 代码注释明确支持 6px | 反驳证据 |
| 产品决策 | 2026-08-14 "6px 圆润"改版是经过评审的产品决策 | 反驳证据 |

**回应**: 设计原则确实支持 2px，但产品注释明确选择 6px。两者冲突。选择 2px 是**回归**而非**进化**，需承认推翻已有产品决策的成本。

---

**质询 A3: 改动 50+ 文件的回归风险如何控制？**

| 风险维度 | 评估 |
|----------|------|
| 文件数量 | 31 个文件、123 处实例（审计严重低估） |
| 视觉一致性 | 2px 圆角在不同组件（按钮、卡片、输入框、面板）上的表现差异需逐一验证 |
| Studio 影响 | Studio 是核心创作工具，圆角变化影响预览一致性 |
| 回滚成本 | 123 处改动需全部还原，回滚工作量大 |

**回应**: 渐进式替换策略在实际操作中不可行——要么全部改，要么不改。分批替换会导致中间状态（部分 2px、部分 6px）更丑、更不一致。这意味着方案 A 实际上是一个**原子性大变更**，与高"故障安全"评分矛盾。

---

**质询 A4: 如果用户偏好圆润风格怎么办？**

| 分析 | 说明 |
|------|------|
| 现状 | 6px 已成为产品现实已超过一周（8-14 起） |
| 用户适应 | 部分用户已适应 6px 圆润风格 |
| 切换成本 | 一旦切换到 2px，偏好圆润的用户将要求切回 |
| 主题层灵活性 | 已有 `--radius-base` CSS 变量，主题可覆盖 | 

**回应**: Design Language 系统（§10）提供了 radius scale 参数（0/2/4/8）。主题作者可在 manifest 中自定义。这意味着**无需全局切换 2px**，保持 6px 默认、主题自行选择更合理。

---

### 1.2 对方案 B「精准校准·渐进演进」的质询

**质询 B1: 6px 圆润是否符合 Quiet Workbench 设计原则？**

| 论据 | 分析 |
|------|------|
| Swiss 原则（历史参考） | 强调锐利几何 → 更倾向 0-2px |
| International Typographic Style | Dieter Rams/ Braun → 直角至上 |
| 实践变体 | Swiss 风格在 UI 落地上有 default (2px) 和 soft-rounded (8px) 两档（历史方案参考，见 §10.6） |
| 产品定位 | AgentSkin 是工具型应用（Premiere/CapCut 对标），非纯瑞士印刷 |

**回应**: 6px 圆润是 Quiet Workbench 风格在 UI 工具场景的合理选择。`design-tokens.md` §10.6 预设注册表中 `soft-rounded` 使用 8px + cozy spacing。选择 6px 是 default (2px) 和 soft-rounded (8px) 之间的中间值，作为 Quiet Workbench 灵活档位的默认值。文档中明确记录为 **"Quiet Workbench 圆角档位 (0/2/4/8px)"**。

---

**质询 B2: "渐进式"是否会导致长期技术债？**

| 模式 | 分析 |
|------|------|
| 渐进式优点 | 每批可独立回滚、不推翻现有风格 |
| 渐进式风险 | 改动分散在 3 个迭代中，期间可能因优先级变化而中断 |
| 技术债 | 如果 P2 批次（动效时长、工具类推广）被无限延期，核心问题仍在 |
| 维护成本 | 文档与代码同步的人工维护成本持续存在 |

**回应**: 渐进式的最大风险是**半途而废**。P0（圆角统一+阴影+文档）收益最高，必须确保在第一批交付。P1/P2 可降级为"有空就做"。关键是第一批必须完整、独立交付价值。

---

**质询 B3: 文档与代码同步的维护成本是否被低估？**

| 事件 | 证据 |
|------|------|
| 当前偏差来源 | 8-14 "6px 圆润" 改版未同步更新 `design-tokens.md` |
| 文档版本 | `design-tokens.md` v2.0 (2026-08-21) 仍记录 `--radius: 2px` |
| 维护机制 | 当前无 CI 检查文档与代码一致性 |
| 变更频率 | 设计系统变更频繁（Design Language 系统、Extended Colors 系统均为 v2.6+ 新增） |

**回应**: 维护成本确实被低估。当前偏差 14 处，若每次设计变更都需手动同步文档，年化成本可观。中期解法是在 globals.css 头部嵌入机器可读注释（已有文档建议 §13.5 #5），短期只能靠开发纪律。

---

**质询 B4: 是否有更好的中间路线？**

| 可能性 | 分析 |
|--------|------|
| 保持 6px + 清理不一致 | 这就是方案 B 本身 |
| 引入 Design Language radius scale | 更灵活，但增加复杂度 |
| 双轨制（内部 Swiss 2px，Studio 6px，历史方案） | 增加心智负担，不推荐 |

**回应**: 方案 B 本身就是中间路线。更好的中间路线是**"方案 B + 中期 Style Dictionary 评估"**，但避免在第一步引入 Style Dictionary。

### 1.3 对方案 C「系统重构·长期演进」的质询

**质询 C1: Style Dictionary 的学习曲线是否被低估？**

| 维度 | 评估 |
|------|------|
| 团队规模 | AgentSkin 前端核心开发者极少（1-2 人） |
| Style Dictionary 复杂度 | JSON/YAML token 定义 + Transform 管道 + Format 输出 + 自定义扩展 |
| 与 Tailwind v4 集成 | Tailwind v4 使用 CSS-first 配置（`@theme inline`），与 Style Dictionary 输出需桥接 |
| 已有 Design Language 系统 | `scripts/design-language.mjs` + `scripts/extended-colors.mjs` 已提供类似功能 |

**回应**: 学习曲线**确实被低估**。AgentSkin 已有 hand-rolled 的 Design Language 系统（§10），提供了密度倍率、圆角档位、阴影档位、动画节奏的组合。引入 Style Dictionary 需要：(a) 将现有 CSS 变量迁移到 JSON token 文件；(b) 编写 Transform 适配 Tailwind v4 的 `@theme inline`；(c) 修改 `build-palette.mjs` 等脚本消费新 token。保守估计 2-4 周。

---

**质询 C2: 1-2 月的迁移周期是否现实？**

| 阶段 | 估算 |
|------|------|
| Token 定义 | 1-2 周（将 globals.css 671 行转为 JSON） |
| Transform 管道 | 1 周（适配 Tailwind v4 输出格式） |
| 组件迁移 | 1-2 周（123 处圆角 + 6 处阴影 + 12 处动画） |
| 主题适配 | 1 周（4 个内置主题） |
| 测试回归 | 1-2 周 |

**总计**: 5-8 周（非 1-2 月，估算基本合理）。但需占用全部开发时间，期间其他功能开发停滞。

---

**质询 C3: 是否有更轻量的令牌管理方案？**

| 方案 | 优点 | 缺点 |
|------|------|------|
| **CSS 原生层**（`@theme inline`） | 零依赖、Tailwind v4 原生 | 无多平台输出、无 JSON 源 |
| **Design Language 系统**（已有） | 已运行、支持密度/圆角/阴影/动画 | 仅覆盖布局参数，不覆盖颜色/字号 |
| **Style Dictionary** | 完整令牌链 | 重依赖、需迁移 |
| **Tiny-tokens (Cobalt UI)** | 轻量、JSON 原生 | 社区小、不活跃 |
| **Tokens Studio + Figma** | 设计-开发同步 | 增加 Figma 耦合 |

**回应**: AgentSkin 实际上**已有**轻量令牌管理（Design Language + Extended Colors），覆盖了布局参数。缺失的是**颜色层级管理**。方案 C 的 Style Dictionary 是全量方案，对当前需求（文档同步 + 圆角统一）是过度工程。

---

**质询 C4: 当前团队规模是否适合引入新工具链？**

| 约束 | 评估 |
|------|------|
| 开发人力 | 1-2 人 |
| 并行任务 | CDP 注入引擎、适配器、Studio 持续开发 |
| 工具链维护 | Style Dictionary 版本升级、Transform 兼容性 |
| AGENTS.md 约束 | 禁止盲目引入新框架 |

**回应**: 不适合。引入 Style Dictionary 后，需持续投入维护精力，挤占核心功能开发时间。

## 四、方案 D 推演

### 4.1 设计目标

基于交叉质询发现，方案 D 应满足：
1. 吸收方案 B 的低风险、高兼容性
2. 吸收方案 C 的令牌管理长期价值
3. 吸收方案 A 的圆角灵活性追求（通过 Quiet Workbench 档位配置实现，非强制）
4. 规避方案 A 的大改动、方案 B 的半途而废风险、方案 C 的工具链复杂度

### 4.2 方案 D「分层校准 + Design Language 深化」

**核心理念**: 保持 6px 默认圆角，但通过 Design Language 系统让每个主题自行选择圆角档位（0-8px）。渐进式清理违规，同时**深化现有 Design Language 系统**而非引入新工具链。
